## Contract completeness rule

HYPOTHESIS for later implementation: every capability should carry all ten requested dimensions even when some values are explicitly unknown: native caller; actual account guards; fresh physical target/range; UI/FSM restrictions; exact arguments; pacing/deadline; correlated result; activity/resource/location conflicts; cancellation/failure; server-only unknowns. A record with an unknown essential precondition cannot become an executable capability merely because the action label is known.

Common future cancellation conditions: owner Pause/Stop, account readiness loss, death/respawn, replaced scene target, changed offer/quest/egg, deadline expiry, budget/space/entitlement loss and a conflicting movement lease. Cancel prevents new dispatches; already sent transactions need result reconciliation. Retry counts/time/spend must be bounded, and a timeout cannot imply a safe repeat. No automation loop or request was implemented in this session.

Compatible work is a future research recommendation: stationary ID pickup collection may continue only with unchanged location ownership and demonstrated non-interference. Claims with inventory/currency changes must share the one scheduler's spend and verification state. Cancellation prevents NEW requests; it cannot be assumed to undo a sent server transaction.
