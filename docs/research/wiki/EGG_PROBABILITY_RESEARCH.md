**Conditional model:** if that sampler and complete transformed pool actually govern an outcome, `p_i=w'_i / sum_k(w'_k)`. Keep UI-hidden outcomes and duplicate pool occurrences in the denominator unless an authoritative rule excludes them. A single pet's annotation can be overwritten by catalog postprocessing; use each egg's own pool. This model is hypothetical with respect to the unseen final hatch handler.

For a normalized pool with a target subset's original mass P, multiplying only that subset's weights by m, with no donor subtraction, gives:

`P' = mP / (1 + (m-1)P)`

It multiplies **odds** P/(1-P) by m; it generally does not multiply final probability by m. For a particular member of that subset, `p_i'=m p_i / (1+(m-1)P)`. A direct `m p_i` approximation requires transformed extra mass to be negligible. Illustrative P0.00001 and m1000 gives about0.00990109, compared with an unnormalized0.01; the numbers are arithmetic examples, not BGSI estimates. If several targeted entries dominate total mass, the difference is larger.

The native Epic stage has a4 cap and different donor handling; subsequent stages can target overlapping subsets. Donor clamping changes the total. The subset formula above must not be applied blindly to every native stage. General/Secret/Infinity/Celestial eligibility and transform order require the actual source inputs and pet fields.

## Useful outcomes start from the best feasible owned team

Let owned inventory P include amount, variants, XP, enchants, IDs and protections. Feasible teams F(P) obey equip/Super/stack constraints. For objective c, `U*_c(P)=max_{T∈F(P)} U_c(T)`; outcome x's marginal improvement is `Δ_c(x)=U*_c(P+x)-U*_c(P)`. Then `q=Σ_{Δ_c(x)>0}p_x`, and initial expected utility gain is `Σ_x p_x Δ_c(x)`.

This definition separates free improvement from already owned pets from improvement purchased through hatching. It also handles an unwanted rare pet that is individually strong but does not improve the objective. Received inventory and effective helper fidelity are essential; catalog rarity alone supplies neither q nor personalized ROI.

The useful set changes as the team improves, duplicates accumulate, recipe prospects change, use-count enchants expire or storage fills. Initial expected gain multiplied by n overstates value when marginal slots saturate. Example, one slot starts with score10 and one possible upgrade has score100 and per-hatch chance p: after n independent hatches, expected best-slot gain is `90[1-(1-p)^n]`, not `90np`. Extra identical copies add no slot utility in this one-slot example. Other Index/quest/recipe benefits require separate explicit goals and cannot be invented.

## Geometric, binomial and batch waiting

The following derivations assume independent stationary eligible trials, fixed per-hatch useful probability0<q<1 and no pity/guarantee/expiry/rotation/delete/storage interference. At q=1, the first eligible trial succeeds and any positive confidence threshold needs one trial; at q=0, no finite success budget exists.

- First useful hatch N: `P(N>n)=(1-q)^n`; `E[N]=1/q`.
- At least one in n: `1-(1-q)^n`.
- Confidence r requires `n_r=ceil(log(1-r)/log(1-q))`; this is a probability threshold, never a guarantee.
- Exactly k in n: `C(n,k)q^k(1-q)^(n-k)`; at least k subtracts the0..k-1 binomial terms.
- Expected successes nq is a count expectation, not success probability; at n≈1/q the probability of any success approaches1-e^-1≈63.2%.
- Batch b: `Q_b=1-(1-q)^b`; expected first successful **batch** count1/Q_b.

With equal cycle time T and results credited only after each batch, `E[time to first successful batch]=T/Q_b`. `T/(bq)` is a rare-arrival approximation and may underestimate first-success wait. For q1,b12, T/Q_b=T while T/(bq)=T/12; the distinction is material even though rare q makes them nearly equal.

## Variable odds, hazard and expiry

For a **known deterministic eligible schedule** of independent hatches, per-hatch q_j can vary. Survival is `S_n=Π_j(1-q_j)`; cumulative discrete hazard `Λ_n=-Σ_j log(1-q_j)`; success `1-exp(-Λ_n)`. For batch j with b_j same-probability trials, its hazard contribution is `-b_j log(1-q_j)`. For very small q, Λ≈Σ b_jq_j. This is a Poisson approximation, not a certified BGSI RNG rule.

If probability depends on random prior results/team state, a single predetermined q schedule is insufficient; condition on the state/history and integrate across paths. Pity, Golden triggers, buff depletion and conditional rerolls can break stationarity or independence. Model branches rather than silently retaining geometric q.

Timer budget: if T_rem is remaining timer and d setup/travel, useful time is at most max(0,T_rem-d), further capped by actual eligibility, storage and spendable currency. Uses-limited boosts require remaining eligible-use count; timer seconds cannot be substituted for uses. Recompute at rotation/expiry/budget/record changes. A current bounty target adds a goal-specific outcome only if the dynamic native pool and actual target match.

## Money, throughput and bounded value

Let per-hatch cost c, batch count b and measured cycle T. Potential spend rate is bc/T. Speed or capacity improves opportunities per time while also spending faster; it does not automatically improve benefit per currency. For n bounded trials, budget is nc before refunds/discount changes. Conditional mean cost to first useful is c/q in a per-hatch stoppable geometric model. If every batch prepays all b trials before stopping, mean paid cost is b*c/Q_b, with Q_b=1−(1−q)^b; this retains the cost of other draws in the successful batch. Neither expectation is a safe unbounded-spend policy.

Protect balances by exact currency key and already committed future costs. Earning opportunity cost, travel, presentation, equip and verification time belong in the same horizon. [Stage1 payback](../replicatedstorage/ECONOMY_AND_ROI.md#payback-includes-time-and-reserves) remains the reusable comparison. No conversion rate between Coins/Gems/event currency/items is assumed; no reserve exception is designed or implemented.
